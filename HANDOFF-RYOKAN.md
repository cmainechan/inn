## Ground-contact shadows and reflection
- Every cat and item shares one 480x400 canvas with the same BASELINE_PAD (process_art.py), so one SVG ellipse, in the same 120x100 viewBox the empty-mark ovals already use, sits at the right ground-contact spot under all of them with no per-item tuning (`.shadow` CSS class, `SHADOW_SVG` constant in index.html). Code-drawn, not baked into the art — the item prompt spec already excludes cast shadows for this reason.
- Cats only get this shadow for the `lie` pose (ball, yarn, takoyaki) — the one case where the cat is on open floor beside the item. Every other pose (sit, sleep, head, half, soak) has the cat on, in, or behind the item, so the item's own shadow already grounds the pair. Learned this the hard way: giving every pose a shadow made it visually overlap the cat itself for a pose whose art sits close to its own baseline (the "head" peeking pose on taiyaki/mochi, where the chin/paws are already near the canvas bottom).
- XL baths skip the shadow entirely — the basin shape already grounds them, and the ellipse would smudge across two spot-widths.
- Shadow strength is tuned, not guessed: measured the panorama's own painted window-shadows directly (lit floor patch vs. a shadow-stripe patch in shokudo, luminance ratio ~0.90, i.e. the art only darkens the floor by ~10%). An untuned multiply-blend ellipse darkens far harder than that by default (~70%+), so fill colour/opacity were lightened to land close to the art's own ~10-20% range. Floor type varies the opacity a bit further: tatami (zashiki) strongest, glossy wood (shokudo, engawa) softest, stone (onsen) in between.
- shokudo (most polished floor, painted with soft window-light reflections) also gets a faint flipped, fade-masked reflection under its items (`.reflection` class) — items only, not cats, since a cat's silhouette varies too much by pose for one flat mask to work.
- Non-issue, checked and confirmed: a faint diagonal band sometimes appears to cross a `lie`-pose cat's head/back (seen on Sheleg beside the ball). Verified by disabling `.shadow` entirely that it's not the shadow code — it's the floor's own diagonal window-light stripe showing through small genuine gaps in the cat's silhouette (between the ears, where the tail meets the back), which happens to read as one continuous line. Left alone; not worth engineering around for how rarely it's noticed.

## Cat art pipeline (tools/process_art.py)
- Every cat pose is placed on a shared bottom baseline, then centred on the bottom 8% of its own content (BODY_BAND / body_centre_x), not on the middle of its bounding box. This was a real fix, not cosmetic: box-centring let a cat with a wider tail or paw spread (e.g. Pilpel) land visibly off from another cat (e.g. Tapuz) in the exact same spot, even though the offset in index.html was identical for both. If a new cat looks consistently offset from the others in the same pose, check this before reaching for a per-cat offset.
- READY_POSES in index.html gates which poses can be randomly picked for a visit: currently sit, sleep, lie, head, half, soak, peer, belly1, belly2 (`ride` was removed along with taiyaki-xl). Bug hit once: an item's art and ITEMS.poses both included a pose, but it never appeared in play because the pose was missing from READY_POSES — pickPose() filters against this set regardless of what the item itself offers. If a pose has full art but never shows up live, check this set first before assuming the item config is wrong. Note pickPose() does NOT check that the visiting cat has art for the pose; `tools/check_art.py` warns about this.
- Poses per item: ITEMS[id].poses is the list a visit can randomly draw from (ITEMS[id].pose is still the fallback/default for old saves and for items with only one pose). Stool: sit, sleep. The three baths: half, soak. taiyaki and mochi use `head` (via `pose`, no `poses` list). taiyaki-xl and its `ride` pose were removed entirely (shop entry, art, raw ride-pose PNGs); `load()` drops any owned/placed id no longer in ITEMS, so old saves are safe.

- `tools/process_art.py` caches by content hash in `tools/.art-cache.json` (gitignored, machine-local — delete it any time to force a clean full rebuild). A raw file whose hash matches last run AND whose expected output(s) still exist on disk is skipped entirely; a no-op rerun takes ~1 second. Invalidation is narrow: (1) the cache is wiped when the hash of the script's *shared code* changes — computed from the parsed AST, so comment/whitespace edits do NOT invalidate; (2) name-keyed config (`PER_ITEM_CONFIG`: OBJECT_SIZE, SHADOW_CUT, OBJECT_SHIFT, FRONT_CURVES, FRONT_WALLS, CLEAR_HOLES, DESHADOW, MAIN_BLOB, ITEM_SOURCE, ITEM_RAW_NAME, FLOATING, CENTER_BBOX[_PREFIXES]) is excluded from that hash and fingerprinted per item instead, so editing one entry (e.g. OBJECT_SIZE['ball']) rebuilds only that item (~4s); item cache entries are keyed by item NAME (`item:<name>`), not raw path, so aliases sharing one raw file are tracked separately; (3) `main()` and the cache/validation helpers (`CACHE_EXEMPT`) are NOT hashed — if you change something in `main()` that affects output pixels, bump `CACHE_VERSION`. Two real cross-file dependencies are handled specially: all items/floating overlays share one `item_scale` from the reference cat's (`tapuz`) `sit` pose (if it changes, every item is reprocessed), and `BODY_MATCH` cats (`lie`, `belly1`) derive scale from the roster median for that pose (a cat whose own art is unchanged is silently recomposed if another cat's edit shifts that median). The contact sheet only shows assets reprocessed in that run. TRAP: never run two invocations concurrently (they'd race on the same output files AND the cache file); a full rebuild takes 10+ minutes — if a run drags on, check memory pressure (`sysctl vm.swapusage`, `vm_stat`) before assuming the script broke.
- Input validation (tools/process_art.py `validate_inputs`, runs before anything is processed): cat/object/food raw art must be 600–2000px on the longest side (the shared item scale assumes ~1254px art; a 4096px gym export once broke it — re-export or resize a COPY, don't edit raw/ in place), and opaque images with a two-tone checkerboard around the edge (a transparency preview exported as pixels) are rejected. A failure lists every problem and exits before touching outputs or the cache. `--skip-validation` bypasses it; results are cached by file hash.
- `tools/check_art.py` cross-checks processed art on disk against index.html (it regex-parses CATS, ITEMS, READY_POSES, SELFIE_POSES, DESTINATIONS, BG_VARIANTS, TRIP_OFFSET, CAT_HUG, CAT_TAILS, PANO_SEASONS — if one of those is reshaped, fix the parser there). ERRORs: referenced art missing (cat sit, item, -front/-water, wheel/fish/charm layers, hug/tail overlays, trip bg/ticket, selfie files, panoramas). WARNs: cat art with no CATS entry, unused outputs, stray panoramas, items listing poses not in READY_POSES, poses with no art for a non-`only` cat, SELFIE_POSES counts below the files on disk. It runs automatically after every pipeline run; `python3 -u tools/process_art.py --check` runs it alone, `--no-check` skips it. Standalone: `python3 -u tools/check_art.py` (exit 1 on errors). Current expected warning: cats/kimono/ (no CATS entry yet). yukata is wired in.
- Do NOT try to re-derive a water (or any XL-bath) layer's position/size by measuring pixels in the bath's own 480x400 art file. The bath image renders with `transform: scale(2)` from `transform-origin: 50% 90%` (see ITEMS[id].scale), so a point's position in the unscaled art does not map linearly to where it ends up on screen — a point 57% down the unscaled canvas can render at roughly 24% down the spot once the scale and bottom-anchored origin are applied. I made exactly this mistake once already: the water looked "obviously" mispositioned in a screenshot, I measured the static art pixel-for-pixel, computed what looked like the "correct" numbers, and that broke an already-working layout, because the fix ignored the scale transform. If a bath's water looks off, nudge the existing percentages by eye against the live, scaled rendering (the same way the original numbers were tuned) rather than recalculating from the source art.

## Known non-issues
- Safari + DevTools: resizing the viewport by opening/closing the inspector in Safari can leave the page briefly in a stale layout (e.g. water looking detached from a bath) until a repaint catches up — this is Safari being slow to recompute dvh units and repaint transformed elements on a DevTools-driven resize, not a bug in the game. Doesn't affect real players, who aren't resizing their viewport while playing. A real window resize (not a DevTools toggle) behaves normally.
- When testing through Claude in Chrome, the driven tab is usually backgrounded from the tool's side, so document.hidden is true and the whole CSS animation timeline is frozen — currentTime stays at 0 no matter how long you wait. To actually see an animation, either check it structurally (class, keyframe names, element.getAnimations()) and ask the user to eyeball the real motion, or force a mid-cycle frame with anim.currentTime = ... on each element.
- mcp__claude-in-chrome__resize_window did not actually change the real viewport in this environment (innerWidth/innerHeight stayed put even after a "successful" resize). To test two screen sizes, load the page in two same-origin iframes of different pixel sizes instead and measure inside each.
